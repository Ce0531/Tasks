# 第一部分：计算机基础

## 一、TCP/IP 初识

### 1. 什么是 TCP/IP

- **TCP/IP** 不是一个协议，而是**一组协议的总称**（协议族）。
- 可以把它理解为「互联网世界的通用语言」：所有电脑、手机、服务器之间要通信，都得遵守这套规则。
- 名字里最核心的两个协议：
  - **TCP**（传输控制协议）：负责数据可靠传输
  - **IP**（网际协议）：负责找到对方的地址（IP地址）

### 2. TCP 的特点

| 特点 | 通俗解释 |
|------|----------|
| **面向连接** | 传输数据前必须先「建立连接」，就像打电话先拨号接通 |
| **可靠传输** | 保证数据不丢、不乱、不重复，丢了会自动重传 |
| **字节流** | 数据像水流一样连续传输，没有明确的边界 |
| **全双工** | 双方可以同时发数据和收数据（双向通道） |
| **流量控制** | 发送方不会发太快把接收方冲垮 |
| **拥塞控制** | 网络堵的时候会自动放慢速度，避免雪上加霜 |

> 一句话总结：TCP 像「挂号信」——必须确认对方收到，丢了会重寄，可靠但稍慢。

### 3. TCP 报文结构

TCP 报文 = **TCP头部 + 数据部分**

头部固定 20 字节（可选选项最多再加 40 字节），关键字段：

```
┌─────────────────────────────────────────┐
│  源端口(16)  │  目的端口(16)            │  ← 从哪个程序来，到哪个程序去
├─────────────────────────────────────────┤
│           序列号(32)                    │  ← 本报文段第一个字节的编号
├─────────────────────────────────────────┤
│           确认号(32)                    │  ← 期望收到对方下一个字节的编号
├─────────────────────────────────────────┤
│ 头部长度 │ 保留 │ 6个标志位 │ 窗口大小  │  ← 标志位很重要！见下
├─────────────────────────────────────────┤
│  校验和(16)  │  紧急指针(16)            │
├─────────────────────────────────────────┤
│  选项（可选，最多40字节）               │
├─────────────────────────────────────────┤
│              数据部分                   │
└─────────────────────────────────────────┘
```

**6 个标志位（重点记）：**

| 标志位 | 全称 | 作用 |
|--------|------|------|
| **SYN** | 同步位 | 请求建立连接时设为1 |
| **ACK** | 确认位 | 确认收到数据时设为1 |
| **FIN** | 终止位 | 请求释放连接时设为1 |
| **RST** | 复位位 | 连接出错，强制重置 |
| **PSH** | 推送位 | 让接收方立刻把数据交给应用，不要缓存 |
| **URG** | 紧急位 | 表示有紧急数据，紧急指针生效 |

### 4. TCP 建立连接：三次握手 ⭐

> 为什么需要三次？因为要确认「双方的发送能力和接收能力都正常」，两次不够，四次没必要。

**通俗比喻：**

```
客户端：喂，听得到吗？（SYN）
服务器：听得到，你呢？（SYN+ACK）
客户端：我也听得到，开始说正事！（ACK）
```

**详细流程：**

| 步骤 | 方向 | 报文 | 客户端状态 | 服务器状态 |
|------|------|------|------------|------------|
| 第一次 | 客户端→服务器 | SYN=1, seq=x | SYN_SENT | LISTEN |
| 第二次 | 服务器→客户端 | SYN=1, ACK=1, seq=y, ack=x+1 | SYN_SENT | SYN_RCVD |
| 第三次 | 客户端→服务器 | ACK=1, seq=x+1, ack=y+1 | ESTABLISHED | ESTABLISHED |

- `seq`：自己的序列号
- `ack`：确认号，表示「我收到了你之前的所有数据，下次从这个号开始发」
- 握手完成后，双方都进入 `ESTABLISHED`（已建立）状态，可以传数据了。

### 5. TCP 释放连接：四次挥手 ⭐

> 为什么建立是三次，释放是四次？因为 TCP 全双工，双方都要各自关闭自己的发送通道。

**通俗比喻：**

```
客户端：我说完了，要挂了。（FIN）
服务器：好的，我知道了。（ACK）
服务器：我也说完了，挂吧。（FIN）
客户端：好的，拜拜。（ACK）
```

**详细流程：**

| 步骤 | 方向 | 报文 | 主动方状态 | 被动方状态 |
|------|------|------|------------|------------|
| 第一次 | 主动方→被动方 | FIN=1, seq=u | FIN_WAIT_1 | ESTABLISHED |
| 第二次 | 被动方→主动方 | ACK=1, ack=u+1 | FIN_WAIT_2 | CLOSE_WAIT |
| 第三次 | 被动方→主动方 | FIN=1, ACK=1, seq=w, ack=u+1 | FIN_WAIT_2 | LAST_ACK |
| 第四次 | 主动方→被动方 | ACK=1, ack=w+1 | TIME_WAIT | CLOSED |

- 主动方发完最后一个 ACK 后，会进入 **TIME_WAIT** 状态，等待 **2MSL**（最长报文寿命的2倍）才真正关闭。
- **为什么要等 2MSL？**
  1. 保证最后一个 ACK 能到达对方（丢了对方会重发 FIN）
  2. 让本次连接的所有残留报文在网络中消失，不影响下一次连接

## 二、HTTP 初识

### 1. 什么是 HTTP

- **HTTP**（超文本传输协议）是浏览器和服务器之间通信的规则。
- 它基于 TCP 协议，默认端口 **80**（HTTPS 默认 443）。
- 是**无状态**协议：服务器不记得你上次请求过什么，每次请求都是独立的。

### 2. HTTP 报文结构

HTTP 报文分两种：**请求报文**（浏览器→服务器）和**响应报文**（服务器→浏览器）。

#### 请求报文结构

```
┌──────────────────────────────────────┐
│ 请求行：GET /index.html HTTP/1.1     │  ← 方法 + URL + 版本
├──────────────────────────────────────┤
│ 请求头：                             │
│   Host: www.example.com              │
│   User-Agent: Chrome/120             │
│   Accept: text/html                  │
│   Cookie: ...                        │
│   Content-Type: ...                  │
├──────────────────────────────────────┤
│ 空行（分隔头和体）                   │
├──────────────────────────────────────┤
│ 请求体（可选，POST/PUT才有数据）     │
└──────────────────────────────────────┘
```

**常见请求方法：**

| 方法 | 作用 | 有无请求体 |
|------|------|------------|
| **GET** | 获取资源 | 无 |
| **POST** | 提交数据（如登录、表单） | 有 |
| **PUT** | 上传/更新资源 | 有 |
| **DELETE** | 删除资源 | 无 |
| **HEAD** | 只获取响应头，不要体 | 无 |

#### 响应报文结构

```
┌──────────────────────────────────────┐
│ 状态行：HTTP/1.1 200 OK              │  ← 版本 + 状态码 + 原因短语
├──────────────────────────────────────┤
│ 响应头：                             │
│   Content-Type: text/html            │
│   Content-Length: 1024               │
│   Set-Cookie: ...                    │
│   Cache-Control: ...                 │
├──────────────────────────────────────┤
│ 空行                                 │
├──────────────────────────────────────┤
│ 响应体（HTML/JSON/图片等实际内容）   │
└──────────────────────────────────────┘
```

### 3. 状态码含义 ⭐

状态码是三位数，第一位代表类别：

| 类别 | 含义 | 常见码 |
|------|------|--------|
| **1xx** | 信息性，请求已接收，继续处理 | 100 Continue |
| **2xx** | 成功，请求已正常处理 | **200 OK**、201 Created、204 No Content |
| **3xx** | 重定向，需要进一步操作 | **301 永久重定向**、**302 临时重定向**、**304 未修改（走缓存）** |
| **4xx** | 客户端错误 | **400 请求参数错误**、**401 未认证**、403 禁止访问、**404 资源不存在** |
| **5xx** | 服务器错误 | **500 服务器内部错误**、502 网关错误、503 服务不可用、504 网关超时 |

**高频必记：**
- `200`：成功
- `301`：永久搬家了（搜索引擎会更新地址）
- `302`：临时搬家
- `304`：资源没变，用你本地缓存就行（省流量）
- `400`：你发的请求有问题
- `404`：找不到这个页面
- `500`：服务器炸了

### 4. 完整的 HTTP 请求/响应流程 ⭐

以浏览器输入 `www.example.com` 为例：

```
① 浏览器解析URL → ② DNS解析域名得到IP → ③ 建立TCP连接（三次握手）
→ ④ 发送HTTP请求报文 → ⑤ 服务器处理请求 → ⑥ 服务器返回HTTP响应报文
→ ⑦ 浏览器解析响应 → ⑧ 渲染页面 → ⑨ 断开TCP连接（四次挥手）
```

**详细拆解：**

1. **解析 URL**：浏览器拆出协议（http/https）、域名、端口、路径
2. **DNS 解析**：把域名翻译成 IP 地址（详见 DNS 部分）
3. **TCP 连接**：与服务器 IP 的 80/443 端口三次握手
4. **发送请求**：浏览器组装 HTTP 请求报文发出去
5. **服务器处理**：服务器根据请求路径和方法，返回对应资源
6. **返回响应**：服务器发回 HTTP 响应报文（含状态码、头、体）
7. **浏览器解析**：根据 Content-Type 判断是 HTML、图片还是其他
8. **渲染页面**：如果是 HTML，开始解析并渲染（详见浏览器渲染部分）
9. **断开连接**：HTTP/1.0 默认请求完就断；HTTP/1.1 默认 keep-alive 保持连接复用

# 第二部分：Web 基础

## 一、互联网

### 1. 什么是互联网

- **互联网（Internet）** = 全世界无数个计算机网络互相连接组成的「网络的网络」。
- 核心作用：让不同地方的电脑能互相通信、共享资源。
- 关键基础设施：海底光缆、路由器、交换机、DNS 服务器、数据中心。

### 2. 互联网的核心规则

- 每台联网设备都有一个 **IP 地址**（如 `192.168.1.1` 或 IPv6 长地址），用来定位。
- 数据被拆成一个个**数据包**传输，到达后再组装。
- 通过**路由器**在不同网络之间转发数据包。

### 3. 上网的本质

你在浏览器输入网址 → 你的电脑通过互联网把请求送到远方的服务器 → 服务器把网页数据通过互联网送回来 → 你的浏览器显示出来。

## 二、域名 ⭐

### 1. 什么是域名

- **域名（Domain Name）** 就是网站的「名字地址」，比如 `www.baidu.com`。
- 因为 IP 地址（如 `14.215.177.38`）太难记，人类用域名代替 IP。
- 域名和 IP 是**多对一**关系：一个域名只能对应一个 IP（同一时刻），一个 IP 可以绑定多个域名。

### 2. 域名的结构（从右往左读）

```
        子域名 . 二级域名 . 顶级域名
         www   .  baidu   .   com
```

| 部分 | 名称 | 例子 | 说明 |
|------|------|------|------|
| `.com` | 顶级域名（TLD） | .com / .cn / .org / .net | 由 ICANN 统一管理 |
| `baidu` | 二级域名（SLD） | baidu / google | 你注册的主体名称 |
| `www` | 子域名/三级域名 | www / mail / blog | 自己可以随意设置 |

- 完整域名最后其实有个点 `.`（根域名），平时省略不写：`www.baidu.com.`
- 域名不区分大小写，`WWW.BAIDU.COM` 和 `www.baidu.com` 一样。

### 3. 常见顶级域名

| 域名 | 含义 |
|------|------|
| `.com` | 商业机构（最常用） |
| `.cn` | 中国 |
| `.org` | 非营利组织 |
| `.net` | 网络服务机构 |
| `.edu` | 教育机构 |
| `.gov` | 政府机构 |

## 三、DNS ⭐

### 1. 什么是 DNS

- **DNS**（域名系统，Domain Name System）= 互联网的「电话簿」。
- 作用：把人类好记的**域名**翻译成电脑能用的**IP 地址**。
- 没有 DNS，你就得记住 `14.215.177.38` 这种数字才能上网。

### 2. DNS 解析的完整流程

以访问 `www.baidu.com` 为例：

```
① 浏览器缓存 → ② 操作系统缓存 → ③ 本地DNS服务器（递归查询）
→ ④ 根域名服务器 → ⑤ 顶级域名服务器(.com) → ⑥ 权威域名服务器(baidu.com)
→ ⑦ 返回IP给本地DNS → ⑧ 本地DNS缓存并返回给用户
```

**两种查询方式：**

| 方式 | 谁来查 | 说明 |
|------|--------|------|
| **递归查询** | 本地DNS服务器代劳 | 你问本地DNS「这个域名IP是啥」，它帮你一路查到底，最后给你最终答案 |
| **迭代查询** | 本地DNS自己一步步问 | 本地DNS问根服务器，根说「去问.com服务器」；再问.com，.com说「去问baidu.com服务器」……自己一步步迭代 |

> 用户电脑 → 本地DNS 是**递归**；本地DNS → 根/顶级/权威 是**迭代**。

### 3. DNS 缓存机制

为了快，每一层都会缓存解析结果：
- 浏览器缓存（几分钟）
- 操作系统缓存
- 本地 DNS 服务器缓存（按 TTL 时间）
- 路由器缓存

> 所以改了域名解析后，不是立刻全球生效，要等缓存过期（TTL）。

### 4. DNS 记录类型

| 记录类型 | 作用 |
|----------|------|
| **A 记录** | 域名 → IPv4 地址（最常用） |
| **AAAA 记录** | 域名 → IPv6 地址 |
| **CNAME** | 域名 → 另一个域名（别名） |
| **MX** | 邮件服务器 |
| **TXT** | 文本说明（常用于验证域名所有权） |
| **NS** | 指定该域名由哪个DNS服务器解析 |

## 四、服务器

### 1. 什么是服务器

- **服务器** = 一台「一直开机、专门提供服务」的电脑。
- 它性能强、稳定性高、24小时不关机，放在数据中心（机房）里。
- 你访问网站时，对方就是一台（或一群）服务器在响应你。

### 2. 服务器的分类（按服务类型）

| 类型 | 作用 | 常见软件 |
|------|------|----------|
| **Web 服务器** | 提供网页/HTTP服务 | Nginx、Apache、IIS |
| **数据库服务器** | 存储和查询数据 | MySQL、Redis、MongoDB |
| **文件服务器** | 存储和共享文件 | FTP、SFTP |
| **邮件服务器** | 收发邮件 | Postfix、Exchange |
| **DNS 服务器** | 域名解析 | BIND |

### 3. Web 服务器做什么

- 监听 80/443 端口，接收浏览器的 HTTP 请求
- 根据请求路径找到对应文件（HTML/CSS/JS/图片）
- 组装 HTTP 响应报文发回给浏览器
- 处理动态请求时，把请求转给后端程序（PHP/Node/Java），再把结果返回

### 4. 相关概念

- **IP + 端口** 定位到服务器上的具体程序（如 `1.2.3.4:80`）
- **主机托管/云服务器**：自己买服务器放机房，或租阿里云/腾讯云的虚拟服务器
- **负载均衡**：一台服务器扛不住时，用多台服务器分摊流量

## 五、浏览器

### 1. 什么是浏览器

- **浏览器** = 一个专门用来「请求网页、解析代码、渲染成可视化页面」的软件。
- 主流浏览器：Chrome、Edge、Firefox、Safari。
- 浏览器的核心是**渲染引擎**（如 Chrome 的 Blink、Firefox 的 Gecko、Safari 的 WebKit）。

### 2. DOM 事件流 ⭐

#### 什么是事件流

当你点击页面上的一个按钮时，这个「点击事件」不是只发生在按钮上，而是会在 DOM 树中**从上到下再从下到上**走一遍，这个传播路径就是**事件流**。

#### 事件流的三个阶段

```
捕获阶段（从上往下）        目标阶段        冒泡阶段（从下往上）
  document                        ↓              ↑
    html                          ↓              ↑
      body                        ↓              ↑
        div                       ↓              ↑
          button  ────────────  目标元素  ──────────┘
```

| 阶段 | 方向 | 说明 |
|------|------|------|
| **捕获阶段** | 外→内 | 从 document 开始，逐级向下，直到目标元素的父级 |
| **目标阶段** | 到达目标 | 事件到达实际触发的元素 |
| **冒泡阶段** | 内→外 | 从目标元素开始，逐级向上冒泡回 document |

#### addEventListener 的第三个参数

```js
// false（默认）：在冒泡阶段触发
element.addEventListener('click', handler, false);

// true：在捕获阶段触发
element.addEventListener('click', handler, true);
```

#### 阻止冒泡

```js
event.stopPropagation();  // 阻止事件继续传播（捕获或冒泡都停）
event.stopImmediatePropagation(); // 阻止传播，且同元素其他监听器也不执行
```

### 3. 事件委托 ⭐

#### 什么是事件委托

- 利用**事件冒泡**机制，把原本要给子元素绑定的事件，统一绑在父元素上。
- 父元素通过 `event.target` 判断是哪个子元素触发的，再做相应处理。

#### 代码示例

```html
<ul id="list">
  <li>苹果</li>
  <li>香蕉</li>
  <li>橘子</li>
</ul>
```

```js
// 不使用委托：每个li都绑一个事件（3个监听器）
document.querySelectorAll('#list li').forEach(li => {
  li.addEventListener('click', () => console.log(li.textContent));
});

// 使用事件委托：只在父元素ul上绑1个事件（1个监听器）
document.getElementById('list').addEventListener('click', (e) => {
  if (e.target.tagName === 'LI') {
    console.log(e.target.textContent);
  }
});
```

#### 为什么能减少事件监听数量

- 原本 N 个子元素要绑 N 个监听器，委托后只在父元素绑 **1 个**。
- 新增/删除子元素时，**不用重新绑定事件**（动态元素友好）。
- 减少内存占用，提升性能。

#### 事件委托的代价（缺点）

1. **事件必须支持冒泡**：像 `focus`、`blur` 不冒泡，不能直接委托（可用捕获阶段或 `focusin`/`focusout` 替代）。
2. **判断逻辑复杂**：父元素要写代码判断 `target` 是不是目标元素，层级深时判断麻烦。
3. **可能误触发**：如果不做判断，点击父元素内任何地方都会触发。
4. **性能微小开销**：每次事件冒泡到父元素都要执行判断逻辑（但通常远小于多绑监听器的开销）。

### 4. 浏览器加载过程 ⭐

> 从输入 URL 到页面开始显示，浏览器在「网络层」做了什么。

**完整流程：**

```
① URL解析 → ② 缓存检查 → ③ DNS解析 → ④ TCP连接（三次握手）
→ ⑤ HTTPS握手（如果是https） → ⑥ 发送HTTP请求 → ⑦ 服务器处理
→ ⑧ 返回响应 → ⑨ 浏览器接收响应体 → ⑩ 解析HTML开始渲染
```

**逐步说明：**

1. **URL 解析**：浏览器判断输入的是搜索词还是网址，拆解协议/域名/端口/路径。
2. **缓存检查**：先看浏览器缓存有没有这个资源，有且没过期就直接用（`304` 或直接读缓存），不发请求。
3. **DNS 解析**：域名 → IP（前面讲过）。
4. **TCP 连接**：与服务器三次握手建立连接。
5. **TLS 握手**（HTTPS）：协商加密方式、交换密钥，建立安全通道。
6. **发送 HTTP 请求**：组装请求报文发出。
7. **服务器处理**：服务器路由到对应资源，生成响应。
8. **返回响应**：服务器发回响应报文（状态码 + 头 + 体）。
9. **接收数据**：浏览器接收 HTML 内容。
10. **进入渲染流程**：开始解析 HTML、构建 DOM、渲染页面（见下一节）。

### 5. 浏览器渲染过程 ⭐

> 浏览器拿到 HTML/CSS/JS 后，怎么把它变成你看到的页面。

**渲染流水线（关键步骤）：**

```
解析HTML → 构建DOM树 → 解析CSS → 构建CSSOM树
→ 合并生成渲染树(Render Tree) → 布局(Layout/Reflow) → 绘制(Paint) → 合成(Composite)
```

**逐步说明：**

| 步骤 | 做什么 |
|------|--------|
| **① 解析 HTML** | 把 HTML 标签解析成 DOM 节点，遇到 CSS 链接去加载 CSS，遇到 script 去加载执行 JS |
| **② 构建 DOM 树** | 生成 DOM（文档对象模型）树，是页面的结构骨架 |
| **③ 解析 CSS** | 解析 CSS 代码，计算每个元素的样式 |
| **④ 构建 CSSOM 树** | 生成 CSSOM（CSS 对象模型）树，包含所有样式信息 |
| **⑤ 生成渲染树** | DOM + CSSOM 合并，只包含可见元素（`display:none` 的不在里面） |
| **⑥ 布局（Layout/Reflow 重排）** | 计算每个元素在页面上的**位置和大小**（坐标、宽高） |
| **⑦ 绘制（Paint 重绘）** | 根据布局结果，把元素的**像素颜色**画出来（文字、颜色、边框、阴影等） |
| **⑧ 合成（Composite）** | 把多个图层合并成最终屏幕上显示的画面 |

#### 重排（Reflow）和重绘（Repaint）

| 概念 | 触发条件 | 性能影响 |
|------|----------|----------|
| **重排（回流）** | 元素的**位置或大小**变了（如改宽高、改display、增减元素） | 代价大，会重新走布局+绘制 |
| **重绘** | 元素的**外观**变了但位置大小没变（如改颜色、改背景） | 代价较小，只重新绘制 |

> 重排一定触发重绘，重绘不一定触发重排。

#### 性能优化建议

- 避免频繁操作 DOM（批量修改，用 `DocumentFragment` 或先 `display:none` 再改）
- 用 `transform` 和 `opacity` 做动画（只触发合成，不触发重排重绘）
- 避免频繁读取 `offsetWidth`、`scrollTop` 等属性（会强制刷新渲染队列）
- CSS 选择器尽量简单，减少层级

#### JS 对渲染的影响

- HTML 解析遇到 `<script>` 会**暂停解析**，先下载并执行 JS（因为 JS 可能修改 DOM）。
- 解决办法：`<script defer>`（下载不阻塞，HTML解析完再执行）、`<script async>`（下载不阻塞，下载完立即执行）。
- CSS 加载不会阻塞 HTML 解析，但会阻塞渲染（渲染树需要 CSSOM）。

### 6. 事件循环 ⭐

#### 为什么需要事件循环

- JavaScript 是**单线程**的（同一时间只能做一件事）。
- 但页面又要处理点击、定时器、网络请求等异步任务，不能一直等。
- **事件循环（Event Loop）** 就是 JS 处理异步任务的调度机制。

#### 核心概念

| 概念 | 说明 |
|------|------|
| **调用栈（Call Stack）** | 当前正在执行的代码，后进先出 |
| **任务队列（Task Queue）** | 存放异步回调，分宏任务和微任务 |
| **宏任务（Macrotask）** | script整体、setTimeout、setInterval、I/O、UI渲染 |
| **微任务（Microtask）** | Promise.then/catch/finally、MutationObserver、queueMicrotask |

#### 执行顺序（必背）

```
1. 执行当前宏任务中的同步代码
2. 执行完所有微任务（清空微任务队列）
3. （可能）执行一次UI渲染
4. 取下一个宏任务执行
5. 回到第2步，循环往复
```

**口诀：先同步，再微任务，然后下一个宏任务。**

#### 代码示例

```js
console.log('1'); // 同步

setTimeout(() => {
  console.log('2'); // 宏任务
}, 0);

Promise.resolve().then(() => {
  console.log('3'); // 微任务
});

console.log('4'); // 同步

// 输出顺序：1 → 4 → 3 → 2
```

### 7. Headless Browser

#### 什么是 Headless Browser

- **Headless Browser（无头浏览器）** = 没有图形界面的浏览器。
- 它能像正常浏览器一样解析 HTML、执行 JS、渲染页面，但你看不到窗口，一切在后台运行。

#### 常见工具

| 工具 | 说明 |
|------|------|
| **Puppeteer** | Google 出的，控制 Chrome/Chromium（Node.js） |
| **Playwright** | Microsoft 出的，支持 Chrome/Firefox/Safari 多浏览器 |
| **Selenium** | 老牌自动化测试工具，支持多语言 |

#### 典型用途

- **自动化测试**：模拟用户操作，测试网页功能是否正常
- **爬虫**：爬取需要 JS 渲染的动态页面（普通爬虫拿不到 JS 生成的内容）
- **截图/PDF生成**：把网页截成图片或导出 PDF
- **性能分析**：自动化测量页面加载性能
- **SSR 预渲染**：预渲染 SPA 页面，提升 SEO

### 8. WebView

#### 什么是 WebView

- **WebView** = 嵌在原生 App 里的「浏览器控件」。
- 它让 App 可以直接显示网页内容，不用跳转到外部浏览器。
- 本质上是一个简化版的浏览器内核（Android 用 Chrome 的 WebView，iOS 用 WKWebView）。

#### 典型场景

- 微信里打开公众号文章、小程序（部分）
- 淘宝、京东 App 里的活动页面
- 很多 App 的「帮助中心」「用户协议」页面
- 混合开发（Hybrid App）：用 HTML/CSS/JS 写页面，套个原生壳

#### WebView vs 普通浏览器

| 对比 | WebView | 普通浏览器 |
|------|---------|------------|
| 界面 | 无地址栏/工具栏，嵌在App里 | 完整浏览器界面 |
| 权限 | 可通过 JSBridge 调用 App 原生能力（相机、定位等） | 只能用浏览器标准 API |
| 性能 | 受 App 限制，可能不是最新内核 | 内核更新及时 |
| 调试 | 需要远程调试（Chrome inspect / Safari 调试） | 直接 F12 |

# 第三部分：额外思考题解答

## 思考题1：一次打开网页的过程中，哪些环节是"网络层"的问题，哪些是"浏览器渲染层"的问题？

### 网络层问题（数据怎么从服务器送到浏览器）

| 环节 | 可能的问题 |
|------|------------|
| DNS 解析 | 域名解析失败、解析慢、DNS 污染 |
| TCP 连接 | 连接超时、三次握手失败、网络不通 |
| HTTPS 握手 | 证书无效、TLS 版本不兼容 |
| HTTP 请求/响应 | 404、500、请求超时、响应体过大 |
| 数据传输 | 丢包、带宽不足、网络延迟高 |

> 网络层的问题表现为：**请求发不出去、响应回不来、回来得慢、回来的是错误码**。

### 浏览器渲染层问题（数据到了之后怎么显示）

| 环节 | 可能的问题 |
|------|------------|
| HTML 解析 | 标签不规范、JS 阻塞解析 |
| CSS 解析 | CSS 加载慢阻塞渲染、选择器复杂 |
| 布局（重排） | 频繁重排导致卡顿 |
| 绘制（重绘） | 复杂样式导致绘制慢 |
| JS 执行 | 长任务阻塞主线程、死循环 |
| 资源加载 | 图片太大、字体加载慢导致闪烁 |

> 渲染层的问题表现为：**白屏时间长、页面闪烁、滚动卡顿、动画掉帧、布局错乱**。

### 一句话区分

- 数据**还没到浏览器** → 网络层问题
- 数据**已经到浏览器了，但显示不对/慢** → 渲染层问题

## 思考题2：DNS 的存在解决了什么问题？如果没有 DNS，用户体验会变成什么样？

### DNS 解决了什么问题

1. **记忆问题**：人类记不住 `14.215.177.38` 这种数字 IP，但能记住 `www.baidu.com`。
2. **IP 变更问题**：服务器 IP 可能会变（换机房、扩容），但域名可以不变，用户无感知。
3. **负载均衡**：一个域名可以解析到多个 IP，DNS 轮询把用户分到不同服务器。
4. **CDN 调度**：DNS 可以根据用户地理位置，返回最近的 CDN 节点 IP，加速访问。
5. **统一入口**：用户只需要记域名，不用关心背后有多少台服务器。

### 如果没有 DNS，用户体验会怎样

1. **上网全靠记数字**：你得记住每个网站的 IP 地址，像背电话号码一样，几乎不可能。
2. **服务器换 IP 就失联**：网站一换服务器 IP，所有用户都访问不了，得重新通知新 IP。
3. **无法做负载均衡和 CDN**：所有用户挤同一个 IP，服务器容易崩，访问慢。
4. **无法用虚拟主机**：一个 IP 只能对应一个网站（没有域名区分），服务器资源利用率极低。
5. **互联网规模不可能这么大**：没有 DNS，互联网不可能发展到今天几十亿用户的规模。

> 一句话：没有 DNS，互联网就退化成「靠记 IP 地址的原始时代」，普通人根本没法用。

## 思考题3：事件委托为什么能减少事件监听数量？它的代价是什么？

### 为什么能减少事件监听数量

- **原理**：利用事件冒泡，子元素的事件会冒泡到父元素。
- **传统方式**：N 个子元素，每个绑一个监听器 → **N 个监听器**。
- **事件委托**：只在父元素绑 **1 个监听器**，通过 `event.target` 判断是谁触发的。
- 监听器少了 → 内存占用少了 → 性能更好。
- 额外好处：动态新增的子元素**自动有事件**，不用重新绑定。

### 它的代价是什么

1. **事件必须冒泡**：不冒泡的事件（如 `focus`、`blur`、`mouseenter`、`mouseleave`）不能直接委托。
2. **需要判断逻辑**：父元素里要写 `if (e.target.matches(...))` 来过滤，层级复杂时判断麻烦。
3. **可能误触发**：如果判断条件写得不严，点击父元素内非目标区域也会触发。
4. **依赖事件冒泡**：如果子元素里有人调用了 `stopPropagation()`，事件就冒不到父元素，委托失效。
5. **微小的判断开销**：每次事件都要执行 target 判断，但通常远小于多绑监听器的开销，整体还是赚的。

## 思考题4：事件循环和"异步"之间的关系是什么？你能举一个页面卡顿可能出现的原因吗？

### 事件循环和异步的关系

- **异步**是一种「现在不执行，等某个条件满足了再执行」的编程方式（如 setTimeout、Promise、网络请求回调）。
- **事件循环**是 JS 实现异步的**调度机制**——它决定这些异步回调什么时候、按什么顺序执行。
- 没有事件循环，JS 单线程就无法处理异步任务（要么一直等阻塞，要么错过事件）。
- 关系：**异步是目的，事件循环是实现异步的手段。**

```
异步任务注册 → 回调进入任务队列 → 事件循环按规则调度 → 回调执行
```

### 页面卡顿的一个原因

**原因：主线程被长时间同步任务阻塞（长任务 Long Task）。**

**举例：**

```js
// 一个巨大的循环，同步执行，卡住主线程
document.getElementById('btn').addEventListener('click', () => {
  let sum = 0;
  for (let i = 0; i < 1000000000; i++) {
    sum += i;
  }
  console.log(sum);
});
```

**为什么会卡：**

1. JS 是单线程，这个 for 循环在主线程上同步执行。
2. 执行期间，事件循环无法处理其他任务（点击、滚动、动画、渲染都被阻塞）。
3. 页面表现为：点击没反应、滚动不动、动画掉帧、整个页面"冻住"。
4. 直到循环跑完，主线程才释放，页面恢复响应。

**其他常见卡顿原因：**

- 频繁触发重排（如在循环里不断修改 `offsetWidth`）
- 大量 DOM 操作
- 图片/资源过大，解码慢
- 定时器里有重活，频繁执行
- 内存泄漏导致页面越来越卡

## TCP vs UDP（补充对比）

| 对比 | TCP | UDP |
|------|-----|-----|
| 连接 | 面向连接 | 无连接 |
| 可靠性 | 可靠，丢包重传 | 不可靠，可能丢 |
| 速度 | 稍慢 | 快 |
| 顺序 | 保证有序 | 不保证 |
| 适用 | 网页、文件传输、邮件 | 视频直播、游戏、DNS查询 |

## HTTP/1.0 vs 1.1 vs 2.0（补充对比）

| 版本 | 特点 |
|------|------|
| HTTP/1.0 | 默认短连接，每次请求都新建TCP连接 |
| HTTP/1.1 | 默认长连接(keep-alive)，管道化，新增方法 |
| HTTP/2.0 | 多路复用、头部压缩、服务器推送、二进制帧 |

## 浏览器渲染优化速记

```
减少重排 → 批量改DOM、用class批量改样式
减少重绘 → 避免频繁改颜色/阴影
用transform/opacity做动画 → 只走合成层
图片懒加载 → 减少首屏压力
JS放底部或用defer → 不阻塞HTML解析
```

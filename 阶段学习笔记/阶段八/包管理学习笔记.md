## 一、包管理基础
### 1. 包（package）
包是预先编写、可直接复用的代码集合
- 日期处理：`moment`、`dayjs`
- 前端框架：`vue`
- HTTP 请求：`axios`
每个包为一个目录，包含功能代码与说明文件（package.json）
### 2. 包管理
包管理是自动完成包的下载、安装、更新与删除的工具，无需手动从官网获取代码并解压
### 3. 包管理的作用
| 痛点 | 无包管理 | 有包管理 |
| --- | --- | --- |
| 下载代码 | 官网查找、手动下载解压 | 一行命令自动下载 |
| 依赖关系 | 手动递归处理依赖链 | 自动递归安装全部依赖 |
| 版本控制 | 版本不明确，团队不一致 | 自动记录版本，全员统一 |
| 更新删除 | 手动操作，易出错 | 命令行更新/删除 |
| 重复安装 | 各项目独立复制 | 缓存复用 |

## 二、三大包管理工具
### （一）npm
#### 1. 概述
- npm = Node Package Manager，Node.js 官方包管理器
- 随 Node.js 自动安装，无需额外配置
- 生态最成熟、使用最广泛
#### 2. 环境验证
```
node -v    # 查看 Node 版本
npm -v     # 查看 npm 版本
```
#### 3. 常用命令
**初始化项目**
```
npm init        # 交互式生成 package.json
npm init -y     # 使用默认值直接生成
```
**安装依赖**
```
npm install                 # 安装 package.json 中全部依赖
npm i                       # 简写
npm install axios           # 安装生产依赖
npm i axios                 # 简写
npm install -D sass         # 安装开发依赖（--save-dev）
npm install vue@3.4.0       # 安装指定版本
npm install -g pnpm         # 全局安装
```
**卸载与更新**
```
npm uninstall axios         # 卸载包
npm remove axios            # 等价写法
npm uninstall -g pnpm       # 卸载全局包
npm update axios            # 更新至兼容最新版
```
**运行脚本**
```
npm run dev                 # 启动开发服务器
npm run build               # 打包项目
npm run preview             # 预览打包结果
```
**查看信息**
```
npm list                    # 查看项目依赖
npm list -g                 # 查看全局依赖
npm list axios              # 查看指定包版本
```
#### 4. 安装流程
```
npm install axios
1. 从 registry 检索 axios
2. 下载包代码
3. 解析 package.json，获取子依赖（如 follow-redirects）
4. 递归下载全部传递依赖
5. 解压至 node_modules
6. 生成/更新 package-lock.json
7. 写入 package.json 的 dependencies
```

### （二）yarn
#### 1. 概述
- Facebook 于 2016 年发布，旨在解决 npm 早期速度慢、安装结果不确定的问题
- 引入 `yarn.lock` 锁文件，保证安装一致性
- npm 后续已吸收其优点，两者差距缩小
#### 2. 安装
```
npm install -g yarn
yarn -v
```
#### 3. 命令对照
| 操作 | npm | yarn |
| --- | --- | --- |
| 初始化 | `npm init -y` | `yarn init -y` |
| 安装全部 | `npm install` | `yarn` / `yarn install` |
| 生产依赖 | `npm install axios` | `yarn add axios` |
| 开发依赖 | `npm install -D sass` | `yarn add -D sass` |
| 全局依赖 | `npm install -g pnpm` | `yarn global add pnpm` |
| 卸载 | `npm uninstall axios` | `yarn remove axios` |
| 更新 | `npm update axios` | `yarn upgrade axios` |
| 运行脚本 | `npm run dev` | `yarn dev` |
| 锁文件 | package-lock.json | yarn.lock |
#### 4. 优缺点
- 优点：并行下载速度快、锁文件一致性强、离线缓存完善
- 缺点：需额外安装、经典版（v1）已进入维护模式

### （三）pnpm
#### 1. 概述
- pnpm = performant npm，2017 年发布
- Vue、Vite、Nuxt 官方推荐
- 核心优势：安装速度快、磁盘占用低、无幽灵依赖
#### 2. 安装
```
npm install -g pnpm
pnpm -v
```
推荐使用 corepack（随 Node.js 自带）：
```
corepack enable
corepack prepare pnpm@latest --activate
```
#### 3. 命令对照
| 操作 | npm | pnpm |
| --- | --- | --- |
| 初始化 | `npm init -y` | `pnpm init` |
| 安装全部 | `npm install` | `pnpm install` / `pnpm i` |
| 生产依赖 | `npm install axios` | `pnpm add axios` |
| 开发依赖 | `npm install -D sass` | `pnpm add -D sass` |
| 全局依赖 | `npm install -g pnpm` | `pnpm add -g pnpm` |
| 卸载 | `npm uninstall axios` | `pnpm remove axios` |
| 更新 | `npm update axios` | `pnpm update axios` |
| 运行脚本 | `npm run dev` | `pnpm dev` |
| 锁文件 | package-lock.json | pnpm-lock.yaml |
#### 4. 核心原理
**全局存储仓库 + 硬链接/符号链接**
**全局存储仓库（Content-addressable store）**
- npm/yarn：各项目独立复制完整依赖，多项目存在多份副本
- pnpm：全局统一存储（`~/.pnpm-store`），同版本仅存一份
**硬链接（Hard Link）**
- node_modules 中的文件通过硬链接指向全局仓库，不占用额外磁盘空间
- 多项目共享同一份物理文件
**符号链接（Symbolic Link）**
- node_modules 根目录仅放置 package.json 中显式声明的包
- 声明的包为符号链接，指向 `node_modules/.pnpm/` 中的真实位置
- 未声明的传递依赖不出现在根目录，杜绝幽灵依赖
#### 5. 幽灵依赖
幽灵依赖指未在 package.json 中声明、但因被其他包依赖而可被 import 的包
示例：项目仅声明 axios，而 axios 依赖 follow-redirects，npm/yarn 扁平化将 follow-redirects 提升至根目录，导致代码中可直接 import 该包，但 package.json 中无记录
风险：
- 依赖升级后子依赖变更，代码突然失效
- 团队环境因版本差异导致不可复现
pnpm 通过严格的目录结构从根本上消除此问题

### （四）三者对比
| 维度 | npm | yarn | pnpm |
| --- | --- | --- | --- |
| 发布时间 | 2010年（随Node.js） | 2016年（Facebook） | 2017年 |
| 额外安装 | 无需 | 需要 | 需要 |
| 锁文件 | package-lock.json | yarn.lock | pnpm-lock.yaml |
| 安装速度 | 较慢 | 较快 | 最快 |
| 磁盘占用 | 高 | 高 | 极低（全局共享+硬链接） |
| node_modules结构 | 扁平化 | 扁平化 | 符号链接 + .pnpm |
| 幽灵依赖 | 有 | 有 | 无 |
| 离线缓存 | 有 | 强 | 最强 |
| Monorepo支持 | 一般 | 优 | 最优 |
| 国内访问 | 需配镜像 | 需配镜像 | 需配镜像 |
| 生态兼容性 | 最好 | 较好 | 良好 |
| 适用场景 | 新手、小型项目 | yarn 存量项目 | 中大型、现代前端项目 |
**选型原则**
- 新手入门：npm
- 存量项目：依据锁文件类型选择，不可混用
- 新项目：推荐 pnpm
- 同一项目仅使用一种包管理工具

## 三、工程结构
Vue + Vite 项目典型目录：
```
my_first_website/
├── node_modules/          # 依赖目录，自动生成，不提交 Git
├── public/                # 静态资源（不经过打包处理）
├── src/                   # 源代码
│   ├── assets/            # 资源文件（经打包处理）
│   ├── components/        # 公共组件
│   ├── router/            # 路由配置
│   ├── stores/            # Pinia 状态管理
│   ├── views/             # 页面组件
│   ├── App.vue            # 根组件
│   └── main.js            # 入口文件
├── .gitignore             # Git 忽略配置
├── index.html             # HTML 入口模板
├── package.json           # 项目配置与依赖清单
├── package-lock.json      # npm 锁文件
├── vite.config.js         # Vite 构建配置
└── README.md              # 项目说明
```
**关键文件**
1. `node_modules/`：第三方依赖，体积大，不提交 Git，由 `npm install` 生成
2. `package.json`：项目配置与依赖清单，必须提交 Git
3. `package-lock.json`：锁文件，记录确切版本，必须提交 Git
4. `.gitignore`：指定 Git 忽略的文件，必含 `node_modules/` 与 `dist/`

## 四、package.json 配置
```
{
  "name": "my-first-website",
  "version": "0.0.0",
  "private": true,
  "type": "module",
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "preview": "vite preview"
  },
  "dependencies": {
    "vue": "^3.4.21",
    "vue-router": "^4.3.0",
    "pinia": "^2.1.7",
    "element-plus": "^2.6.0"
  },
  "devDependencies": {
    "@vitejs/plugin-vue": "^5.0.4",
    "vite": "^5.2.0"
  }
}
```
### 1. 基础字段
| 字段 | 含义 | 示例 |
| --- | --- | --- |
| `name` | 项目名称 | `"my-first-website"` |
| `version` | 项目版本 | `"0.0.0"` |
| `private` | 是否私有（true 不可发布） | `true` |
| `type` | 模块类型，module 表示 ES6 模块化 | `"module"` |
| `description` | 项目描述（可选） | `"仿B站登录页面"` |
| `author` | 作者（可选） | `"name"` |
| `license` | 开源协议（可选） | `"MIT"` |
### 2. scripts
定义可通过 `npm run <name>` 执行的命令
- `dev`：启动开发服务器
- `build`：打包生成 dist
- `preview`：本地预览打包结果
- 支持自定义脚本，如 `"deploy": "gh-pages -d dist"`
### 3. dependencies（生产依赖）
项目运行时所需的包，打包上线后仍需使用。通过 `npm install <pkg>` 安装
### 4. devDependencies（开发依赖）
仅开发阶段所需的包，上线后不需要。通过 `npm install -D <pkg>` 安装
生产环境可使用 `npm install --production` 仅安装 dependencies
### 5. 语义化版本（SemVer）
格式：`主版本号.次版本号.补丁版本号`
| 位置 | 名称 | 递增条件 | 示例 |
| --- | --- | --- | --- |
| 第1位 | major | 不兼容的 API 变更 | 3.4.21 → 4.0.0 |
| 第2位 | minor | 兼容的功能新增 | 3.4.21 → 3.5.0 |
| 第3位 | patch | 兼容的 bug 修复 | 3.4.21 → 3.4.22 |
### 6. 版本范围符号
| 符号 | 含义 | 示例 | 范围 |
| --- | --- | --- | --- |
| `^` | 允许 minor 和 patch 升级 | `^3.4.21` | `>=3.4.21, <4.0.0` |
| `~` | 仅允许 patch 升级 | `~3.4.21` | `>=3.4.21, <3.5.0` |
| 无 | 精确版本 | `3.4.21` | 仅 3.4.21 |
| `*` | 任意版本 | `*` | 最新 |
| `latest` | 最新发布版 | `latest` | 最新 |

## 五、node_modules 结构原理
### 1. npm：扁平化结构
npm v3 起采用扁平化（hoisting）策略，将依赖尽可能提升至 node_modules 根目录
无冲突时：
```
node_modules/
├── A/    # 直接依赖
├── B/    # A 的子依赖，提升至根目录
└── C/    # A 的子依赖，提升至根目录
```
存在版本冲突时，使用频率高的版本放根目录，其余嵌套：
```
node_modules/
├── A/
│   └── node_modules/
│       └── B/  # B@1.0，嵌套
├── D/
└── B/          # B@2.0，根目录
```
**扁平化的问题**
1. 幽灵依赖：未声明的包可被 import
2. 磁盘浪费：各项目独立复制
3. 结构不确定：提升规则复杂，不同 npm 版本结果可能不同
### 2. pnpm：符号链接 + .pnpm
```
node_modules/
├── .pnpm/                # 虚拟存储，存放全部真实包
│   ├── A@1.0.0/
│   │   └── node_modules/
│   │       ├── A/        # 硬链接 → 全局 store
│   │       ├── B/        # 符号链接 → ../../B@1.0.0/...
│   │       └── C/        # 符号链接 → ../../C@1.0.0/...
│   ├── B@1.0.0/
│   │   └── node_modules/
│   │       └── B/        # 硬链接 → 全局 store
│   └── C@1.0.0/
│       └── node_modules/
│           └── C/        # 硬链接 → 全局 store
└── A/                    # 符号链接 → .pnpm/A@1.0.0/...
```
**结构要点**
1. 根目录仅含显式声明的包，均为符号链接
2. 真实包存于 `.pnpm/`，按 `包名@版本号` 组织
3. `.pnpm/` 内文件为硬链接，指向全局 store
4. 包间依赖通过符号链接引用
**优势**
1. 无幽灵依赖
2. 磁盘占用极低
3. 安装速度快（仅创建链接，不复制文件）
4. 依赖结构严格确定
### 3. 性能差异原因
| 方面 | npm | pnpm | 原因 |
| --- | --- | --- | --- |
| 磁盘占用 | 各项目完整复制 | 全局 store 一份 + 硬链接 | 硬链接不占额外空间 |
| 安装速度 | 下载+解压+复制 | 缓存命中时仅创建链接 | 省去下载与复制 |
| 网络请求 | 每次请求 registry | 缓存命中无需请求 | 全局缓存复用 |

## 六、依赖版本冲突与锁文件
### 1. 冲突产生
项目依赖 A 和 D：
- A 依赖 `B@^1.0.0`
- D 依赖 `B@^2.0.0`
B 的 1.x 与 2.x 不兼容，产生版本冲突。
### 2. npm 的处理方式
- 使用频率高的版本提升至根目录
- 其余版本嵌套于对应包的 node_modules 内
- 各依赖使用各自目录下的版本，互不干扰
副作用：结构复杂、多版本共存导致体积增大、可能引发不可预期的问题
### 3. 解决方案
1. 统一版本：尽量使全部依赖使用同一大版本
2. 查看冲突：`npm ls <pkg>`
3. 强制指定：npm 使用 `overrides`，pnpm/yarn 使用 `resolutions`
4. 锁文件：固定确切版本，避免自动升级
### 4. 锁文件
**作用**：记录每个包的确切版本，保证不同时间、不同环境的安装结果完全一致
| 工具 | 锁文件 |
| --- | --- |
| npm | package-lock.json |
| yarn | yarn.lock |
| pnpm | pnpm-lock.yaml |
锁文件必须提交至 Git。`.gitignore` 中不应忽略锁文件，仅忽略 `node_modules/` 与 `dist/`

## 七、阿里 npm 镜像
### 1. 作用
npm 默认从国外服务器（registry.npmjs.org）下载，国内访问缓慢且易超时。阿里镜像将包同步至国内服务器，提升下载速度。
### 2. 配置
```
npm config set registry https://registry.npmmirror.com
```
### 3. 验证
```
npm config get registry
```
输出 `https://registry.npmmirror.com/` 即为配置成功
### 4. 恢复官方源
```
npm config set registry https://registry.npmjs.org
```
### 5. cnpm
cnpm 是淘宝团队基于 npm 的国内镜像封装，默认使用国内源
```
npm install -g cnpm --registry=https://registry.npmmirror.com
```

## 九、难点
| 难点 | 理解 |
| --- | --- |
| 硬链接 vs 符号链接 | 硬链接为同一文件的别名，不占空间；符号链接为指向其他路径的快捷方式 |
| 幽灵依赖 | 未声明但可 import 的包，pnpm 无此问题 |
| ^ 与 ~ | ^ 允许 minor 升级，~ 仅允许 patch 升级 |
| dependencies vs devDependencies | 前者为运行时依赖，后者为开发工具 |
| 锁文件 | 固定确切版本，保证一致性，必须提交 Git |
| 不可混用工具 | 各工具锁文件格式不同，混用导致依赖混乱 |
| .pnpm 目录 | pnpm 虚拟存储，真实包存放于此，根目录为符号链接 |
| 扁平化 | npm 将传递依赖提升至根目录，便利但产生幽灵依赖 |
